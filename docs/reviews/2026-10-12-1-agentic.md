# Review 1 of 3: agentic topology and context flow (vtt 2.0 input)

Reviewer: Principal AI Agent Architect (Fable 5.1). Date: 2026-10-12. Branch `vtt-2.0` (== `main`, e7c58e9).
Read-only. Everything run was run from a copy of the repo built in the scratchpad, with its own
`XDG_DATA_HOME` and a fresh `XDG_RUNTIME_DIR`; the one live vtt I started was stopped by PID.

How to read this: **S1** is the surface "agents as users of the running program" (the control
channel, `--apply`, the map tools); **S2** is "agents as developers of the codebase" (CLAUDE.md,
CODEMAP, docs, module layout). Each finding says *verified* (code read at `file:line`, or a
command run and what it printed) or *inferred*.

What I ran, so the next reviewers can reproduce:
- `./vtt crypt.vtt --apply plan.txt --new 40x24` with AGENTS.md's example plan; then `--dump-map`,
  `--describe [--json]`, `--check [--json]` and byte counts.
- The same on a filled 512x512 map (`tile A1:SR512 floor` + two rooms + a corridor).
- A live vtt under `script` fed from a fifo; `vtt --ctl` probes with the channel off and on:
  `status`, `dump`, `jobs [json]`, `wait 0`, `wait 0 for 0`, `marked [json]`, a proposal, errors,
  `:ask` with a `v` box, `job N take`, `job N propose`, GM accept, the `map changed` event after
  `HHH`, the agent's `undo`.

## 1. Vulnerabilities

Severity: **High** = will produce agent loops, stalls, or silent divergence between what the
agent believes and what is true; **Medium** = token waste or a lossy boundary an agent must work
around; **Low** = paper cut.

### S1-1 (High, S1): the machine-readable protocol is human prose

The channel's verdict line is `ok`, `error: line N: <prose>` or `busy: <prose>`
(`src/app_ctl.c:1498-1499`). No request error carries a stable code; `check` does (`E110`,
`W104`, `src/maptools.c:1067-1096`), so the two halves of the same surface disagree. The
program's own clients already pay for this: `--apply --wait` finds its verdict by matching the
words ` job N accepted`, ` job N scrapped`, ` job N feedback: ` (`src/ctl.c:622-645`), and finds
its job number by `strstr(body, "proposal #")` (`src/ctl.c:713-714`); HEALTH row 16 records
that a reworded event breaks `--wait` silently. Verified live: errors are good prose
(`ZZ99 is not a square on this map (A1 to AN24), nor a room's name`;
`line 3: there is already a creature called Ghoul`) but an agent must regex them to branch.

Why it matters for 2.0: every agent framework will wrap `vtt --ctl` in a tool; a tool whose
failure modes are only prose forces the LLM to classify errors itself on every call, which is
where retry loops come from.

### S1-2 (High, S1 and S2): the verb grammar exists only as scattered string lists

There is no table of requests. The same verb set is kept by hand in: `is_edit`'s `EDITS[]`
(`src/app_ctl.c:1060`), `off_takes` (`:1069-1074`), `lonely` (`:960-967`), `not_alone`
(`:1402-1423`), `scene_is_edit` (`:970`), the 320-line `strcmp` chain in `run_line`
(`:1078-1397`), the GM-only refusal lists in `src/app_ctl_job.c:134-138` and
`src/app_ctl.c:1148-1152`, the three doc tables (AGENTS.md:83-158, CONTROL.md:61-113,
README:1495-1535), the agent prompt's list (`src/app_agent.c:78-79`), and the fuzz seeds.
Verified drift already: the prompt vtt hands a spawned agent lists the edit verbs as
"room, tile, wall, edge, door, corridor, area, token ..., note, fog paint, stamp, link, floor,
scene" — `env` (in `EDITS[]`) is missing. The word `describe` appears in 28 files
(`grep -l -w describe` over README, docs, src, tests, fuzz corpus). There is no `help` request:
an agent cannot discover the grammar at run time; it must have read a 25 KB page.

### S1-3 (Medium, S1): `wait 0` stalls 60 s on a fresh vtt, and the doc says otherwise

AGENTS.md:268-269: "`wait 0` everything still kept (the last 32)". Code: `wait SEQ` is held
unless `app_events_after(a, seq)` is non-zero (`src/app_ctl.c:1250`), and with no event yet
`event_seq - 0 == 0` (`src/app_event.c:36-40`), so the default 60 s hold applies. Verified
live: `vtt --ctl 'wait 0'` on a vtt with one proposal and no events returned `seq 0` after
~60 s. `status` does not report `seq` (`src/app_ctl.c:117-143`), so the only cheap way to learn
where the ring stands, `wait 0 for 0`, is not the documented one. An agent that follows the
page loses a minute at every start.

### S1-4 (Medium, S1): unbounded and padded reads

- Full `dump` of a filled 512x512 map: **541,051 bytes** (measured), roughly 150-200k tokens, in
  one answer; `dump B2:U21` of the same map is 1,412 bytes. The region form is the right
  tool, but nothing refuses or warns on the whole-map form, and `describe` has no region or
  filter form at all (`src/maptools.c:494`): its size follows the room count.
- Every `dump` appends the same 3-line key and the map footer (`src/maptools.c:217-220, 248`):
  ~330 bytes of fixed text per call, on a `job N dump B2:D4` of nine squares too (verified:
  the 3x3 dump was ~560 bytes, over half of it key and footer).
- `describe json` carries every square twice (`"at":"N3","x":13,"y":2`, by design per
  README:1490) and `jobs json` repeats the proposal summary in both `thread[]` and
  `proposal` (`src/app_ctl_job.c:43-67`; verified in the live output).
- There is no delta read. `map changed: walls and doors in Y1` (verified live) names a
  bounding region only; to learn what changed the agent re-dumps the region. The data to do
  better already exists: `checkpoint_changes` yields a `ChangeSet` with before/after per cell
  and per creature (`src/checkpoint.c`, `src/changeset.c:813-869`), and only a summary of it is
  ever written out.

### S1-5 (Medium, S1): one global "the agent" — no identity, shared undo, no review guard

The channel has no notion of who is calling. `ctl_undoable`/`ctl_stamp`/`ctl_gen` are
App-wide singletons set by `land` for any non-disk job (`src/app_job.c:125-129`) and consumed by
`undo` (`src/app_ctl.c:1193-1215`), so with two agents (or vtt's own `:agent command`, which
starts one process per `:ask` and per feedback with no cap, HEALTH row 40) one agent's `undo`
takes back another's accepted change. Any client may `job N take` or `drop` any job
(`src/app_ctl_job.c:140-198`). `app_ctl_busy` (`src/app_ctl.c:99-111`) does not count the
review mode: verified live, `undo` succeeded while `status` reported
`screen build, review mode` (the GM was reviewing job 1 when the agent reverted job 2). The
GM-decides rule is deterministic and correct; the agent side of it is anonymous.

### S1-6 (Medium, S1): conflicts are a count, values land unchecked

`jobs` reports `(N conflicts: changed since)` (`src/app_ctl_job.c:27-29, 65`), never which
elements. Accept applies the set's *values* and skips `floor_problem`/`link_problem`
(CONFLICTS.md:368-371, a recorded tradeoff). The GM sees red squares; the agent, told only
"3 conflicts", can only re-propose blind. `cs_check` already knows each element that no longer
matches (`src/changeset.c:454`); nothing prints them.

### S1-7 (Low, S1): bounded history drops silently

Events: a ring of 32 x 240 chars with `lost A-B` and `reset N` lines (`src/app_event.c:42-57`):
good. Job threads: 8 lines, oldest dropped with no marker (`src/app_job.c:59-62`); the original
ask survives in `Job.text` (`src/job.h:47`), so the loss is of the middle of the conversation.
Event texts are cut with `%.150s`/`%.120s` (`src/app_job.c:140-149`); `jobs` has the whole, as
AGENTS.md:294 says.

### S1-8 (Low, S1): `sun_path` budget

With `XDG_RUNTIME_DIR` under a long path, the client printed `vtt: socket path too long` and
exited 2, and the server had no socket directory (observed on my first run from the scratchpad
path, ~95 chars + `/vtt/<pid>.sock` > 108). An agent sandboxed under a deep temp dir cannot
reach vtt and is told nothing it can act on.

### S1-9 (Low, S1): `describe`'s room identity is two-headed

JSON gives `"name":"B2","area":"Hall"` while text says `room 2 Hall (B2)`; a corridor with
open ends merges rooms (documented, AGENTS.md:198-199), so after the example plan "Hall" is
`B2:G10` and includes the Well's water. Correct, but an agent reading JSON must know that
`name` is a square and `area` is the name.

### S2-1 (High, S2): current truth lives inside design records

CONTROL.md's Status line says truth is the README, AGENTS.md and CODEMAP rows (CONTROL.md:3-7),
yet its *As built* section (CONTROL.md:127-250) holds facts found nowhere else or only
partially elsewhere: `CTL_OPS_MAX`, the 16-job cap and its refusal, "job/jobs lines before
propose", `--apply` exit codes' edge cases, the `wait` hold mechanics. CONFLICTS.md (64 KB)
is the same for proposals. To change the channel safely an agent reads CLAUDE.md (10 KB),
the `app_ctl.c` row (2.1 KB), AGENTS.md (25 KB, "read whole"), CONTROL.md (21 KB), CONFLICTS.md
*Pieces* and *Decisions* (~20 KB) and three README sections: ~90-110 KB of prose for a 1.6
KLOC pair of files. The doc index's rule "do not read a design record to learn what the app
does now" (docs/README.md:26-28) is contradicted by where the facts are.

### S2-2 (High, S2): god object and god file at the agent seam

`App` has 134 fields (`src/app.h:118-363`); the channel, jobs, disk, events and agent-command
state are interleaved there (the comment blocks at `app.h:240-262` already group them, but as
comments, not structs). `src/app_ctl.c` is 1,589 lines; the proposal code cannot move out
because `Edits` is file-private (HEALTH row 1). `run_line` is a single 320-line `strcmp`
chain. Adding one read verb today touches `run_line`, possibly `off_takes`, four doc tables,
`test_ctl.c`, and a fuzz seed — and nothing checks the six agree (S1-2).

### S2-3 (Medium, S2): the load-bearing invariants are prose

Enforced by code or tests (good): `undo_balanced` after every `press()` (`tests/harness.c:130-135`);
`_Static_assert`s on palette/enum drift and on `Link` fitting a token slot (`src/grid.c:97-98`,
`src/undo.c:418,480`, `src/checkpoint.h:57`); the job state machine (`src/job.h:19-25`);
GM-only jobs (`app_job_gm_only`, `src/app_ctl_job.c:134`); `token del` refusing the acting
creature (`src/app_ctl.c:590-592`); the AGENTS.md example plan applies and checks clean
(`tests/test_ctl.c:1197-1211`); LIT/RIM stripped by `undo_set_fog` (CODEMAP fog row).
Prose only: "add every GM-only thing to `app_view_differs`" (per-feature `players_text` tests
exist, 12 files, but no enumeration); "every new silent-drop site calls `diag()`"; "a writer
round the log calls `cp_note`"; "creature numbers go through `app_note_gm`" (HEALTH row 45 is a
slip of exactly this kind, caught by a reader, not a test); the rule of three and the watch
list. No `tools/lint.sh` exists for any of them.

### S2-4 (Medium, S2): CODEMAP rows carry history as well as ownership

Rows are single dense cells: `app_ctl.c` 2.1 KB, `fog.c` and `ruler.c` similar, `tests/`
1.3 KB. They mix what the file owns, its invariants, and change history ("since the health
check", "2026-10-09", "step 7"). The row is the unit an agent is told to read before every
change (CLAUDE.md, *Read on demand*), so the history is paid for on every edit. Coverage is
complete (verified: every `src/*.c` basename appears in CODEMAP.md).

### S2-5 (Medium, S2): the one untestable path is the agent's path

`main.c`'s loop has no test (HEALTH row 9); it is where a `wait` is held and where waiters are
flushed after a key (CODEMAP main.c row; CONFLICTS.md:234-236). Step 5's bug there was found
only by driving a live vtt. For 2.0 the hold/flush contract is the heart of the agent loop and
must be a function a test can call.

### S2-6 (Low, S2): append-only logs are the pointed-to memory

PERFORMANCE.md 90 KB, HEALTH.md 42 KB, CONFLICTS.md 64 KB with a per-step build log. CLAUDE.md
asks every feature to regenerate/append to them. Episodic forms exist (the user's memory dir,
the plans' *Progress* sections, the after-compact hook that prints 5 commits + status + *In
flight*) and are the right idea; the raw logs are still what the rules name as the record.

## 2. Refactoring recommendations (decisions for the 2.0 design)

### Preserve as-is, and why

- **Proposals on a scratch copy, GM decides, all-or-nothing, one undo step**
  (`proposal_begin`/`finish_proposal`, `src/app_ctl.c:979-1056`; `land`, `src/app_job.c:109-154`).
  This is the right deterministic guardrail: the agent is never trusted with the live map,
  and the GM's redo tail, `modified` and `Map.gen` never move for a change nobody accepted
  (CONFLICTS.md:155-164 says why; keep that reasoning).
- **The event ring with `seq`, `lost A-B` and `reset N`** (`src/app_event.c:42-57`). This is a
  textbook resumable cursor; keep the semantics exactly, including "waiters answered after the
  key that made the event".
- **`dump [REGION]`, `marked`, `job N dump|check|describe`** as the bounded reads; the
  region-scoped dump is 1.4 KB where the whole is 541 KB.
- **One request language for file (`--apply`) and live**, and the same `app_ctl_exec` for
  tests, fuzzer, bench and `--apply` (`src/main.c:771-772`).
- **`app_agent_prompt`'s episodic shape** ("Take the job, read the map, propose once, read your
  proposal back, and exit", `src/app_agent.c:77-80`): one run is one attempt, state lives in
  vtt, not in the agent. Keep this as the model for every agent entry point.
- **Jobs as a small state machine with numbers never reused at once** (`src/app_job.c:33-37`),
  the thread, and `jobs json`.
- **The GM-only privacy boundary** (`app_view_differs`, `fog_token_unseen`) and the fact that
  the channel is same-user only (0700 directory, both sides check).
- **Developer side:** CLAUDE.md as rules-only under 150 lines; CODEMAP read by row; the doc
  index with Status lines; HEALTH.md's "never dismiss a finding without a check" rule and the
  *Left open* table; `press()` enforcing `undo_balanced`; the after-compact hook; the tested
  AGENTS.md example.

### Change

**R1. One verb table drives everything (closes S1-2, half of S2-2).**
A `static const Request REQUESTS[]` with: name, kind (read / edit / lonely / job-scoped),
allowed with channel off, allowed with no map, arity and argument shapes, one-line doc, and
the handler — like `app_cmd.c`'s `COMMANDS[]` (`src/app_cmd.c:1118`) already does for `:`.
`off_takes`, `lonely`, `not_alone`, `is_edit` and the dispatcher become lookups. Add a
`help [VERB]` (and `help json`) read generated from the table, and a test that AGENTS.md's
tables list exactly the table's verbs (the existing AGENTS-example test shows how). Generate
the agent prompt's verb list from it.

**R2. A typed envelope with stable codes (closes S1-1).**
Keep the first-line verdict for humans, add a code: `error R301 line 3: there is already a
creature called Ghoul`, with an `errors` table in the README like `check`'s. Events get a
code too (`J10 job 3 accepted: ...`), and `ctl_verdict_in` matches codes, not words. Offer
`json` on the whole answer (`--ctl --json` or a first line `format json`): `{verdict, code,
line, message, fix, body}`. The `fix` field is the sentence the prose already carries
("jobs lists them", ":agent on").

**R3. Reads that cost what changed (closes S1-3, S1-4).**
- `status` prints `seq N` and the job counts.
- Either `wait 0` answers at once when nothing is kept, or AGENTS.md says `wait 0 for 0`.
- `changes SEQ [REGION]`: the change set since the agent's checkpoint, as lines (`tile D4
  floor->water`, `edge G5|H5 wall->door`, `token "Ghoul" C3->D5`, `area Crypt ...`), from
  the `ChangeSet` the checkpoint already builds; keep the summary line as its header.
  This is the delta-scoped read the surface lacks; it costs a formatter, not a subsystem.
- `dump` without a region above some square count answers with the bounds and a hint unless
  `dump all`; the key/footer move behind `dump key` or shrink to one line.
- `describe REGION|AREA` and `describe rooms|creatures|links` filters.
- Drop one of `at`/`x,y` in JSON, or make the duplicate opt-in.

**R4. Agent identity and scoped undo (closes S1-5).**
A request may open with `agent NAME` (or `VTT_AGENT` set by the spawner); jobs record their
taker; `job N undo` replaces the global `undo` for accepted proposals (keep plain `undo` as an
alias for the caller's own last job). `take`/`drop`/`propose` on another agent's job refuse
with a code. `app_ctl_busy` counts `ED_REVIEW` for landing and undo, or the design says
why not. vtt tracks the PIDs it spawns for `:agent command` and refuses a second run of a job
while the first lives (HEALTH 40).

**R5. Conflicts as data (closes S1-6).**
`job N conflicts [json]`: each element whose live value is not the set's `before`, as the
same lines `changes` uses. The GM already sees them in red; the agent should see the list.

**R6. Developer surface: separate truth from history (closes S2-1, S2-4, S2-6).**
- Move every "As built" fact that is still true into the owning CODEMAP row or README section,
  then freeze the design records (Status: "record only; nothing here is current"). The doc
  index's rule becomes true.
- CODEMAP rows become two columns, *owns* and *invariants*, with no dates or step numbers;
  history goes to the design record or HEALTH.md.
- HEALTH.md and PERFORMANCE.md keep an *index* (one table each) at the top and move the
  dated prose below a fold; CLAUDE.md points at the index.

**R7. Developer surface: lint the prose invariants (closes S2-3).**
`tools/lint.sh`, run by `make test`: `fog_token_hidden(` outside fog.c; `memcmp` on a `Token`;
`app_set_status(`/`app_note(` in files whose CODEMAP row says GM-only; a new drop site in
mapio.c without `diag(`; a new `src/*.c` without a CODEMAP row (the loop I ran is the check);
AGENTS.md's verb tables vs `REQUESTS[]` (R1). Each is a grep; each is a rule the repo already
states.

**R8. Developer surface: split App and app_ctl.c along the comment seams (closes S2-2, S2-5).**
`App` gains `Channel ctl`, `Jobs jobs`, `Disk disk`, `Events ev` sub-structs (the groupings
at `app.h:240-262` are already there as comments). `Edits` becomes a header type so
`app_ctl_propose.c` can exist (HEALTH 1). The interactive loop's body becomes
`app_loop_once(App*, const Input*, now_ms)` so a test can hold a `wait` and press a key.

**R9. Don't build an MCP server into vtt; make `vtt --ctl` MCP-ready.**
CONTROL.md:21 already says an MCP wrapper can sit outside. With R1/R2 (a `help json` grammar
and typed answers) a 50-line wrapper can expose each verb as a tool with a schema generated
from `REQUESTS[]`. Keep "no dependencies" by keeping the wrapper outside the binary.

### Drop
- The three parallel hand-kept doc tables of the verb set (generate one, link to it).
- The `proposal #` and event-word scraping in `ctl.c` once codes exist.
- The per-call key block in `dump`.

## 3. Agent-Friendliness Scores

**S1, agents as users: 7/10.** The hard parts are right and rare: a proposal model on a scratch
copy, the GM as the only writer, resumable numbered events with explicit loss, bounded
region reads, all-or-nothing requests that name the failing line, an episodic job prompt, and
one language for file and live. What holds it back is the protocol's skin: prose-only errors
and events (its own `--wait` client scrapes them), no discoverable grammar or `help`, a
documented `wait 0` that stalls a minute, one anonymous "the agent" with a global undo, a
conflict count with no list, and a `dump` that can hand back half a megabyte with a fixed key
on every call.

**S2, agents as developers: 6/10.** The scaffolding for context resets is unusually good:
rules-only CLAUDE.md under 150 lines, a per-file map read by row, a doc index with Status
lines, a findings ledger with a no-dismissal rule, a compaction hook, invariants enforced in
the test harness and by static asserts. But the truth of the agent surface is spread over
~100 KB of prose with current facts inside design records, the rows an agent must read carry
history, a 134-field `App` and a 1,589-line `app_ctl.c` with a 320-line dispatch chain sit
exactly where agent features land, most of the standing invariants are enforced only by an
agent remembering them, and the one path no test reaches is the agent's hold-and-flush loop.

## 4. Open questions for the maintainer

1. **Many agents or one?** Is `:agent command` meant to run several agents at once (one per
   `:ask`, HEALTH 40), or one at a time? R4 (identity, scoped undo, a PID table) follows from
   the answer.
2. **Values or intent at accept?** CONFLICTS decision 2 chose values. Should 2.0 keep the
   plan text with the job so a sent-back or conflicted proposal can be re-run against the map
   as it is now, with the GM seeing a new preview? (Preview-equals-landing would still hold.)
3. **Text or JSON as the canonical wire form?** Today text is primary and JSON is bolted on
   per read. If the LLM is the main client, is `json` the default and text the `--human` view?
4. **How much should the channel give out with `:agent off`** (HEALTH 15)? "Refused, no
   reason" vs. today's "the plan's own lines say why they failed".
5. **Delta reads:** is a `changes SEQ [REGION]` read (R3) acceptable as the answer to "what
   moved under me", or should `map changed` events themselves carry the element list up to a
   size?
6. **The 64 KB request cap and the 240-char event text**: keep, raise, or make the caps part
   of `status`/`help` so an agent can read them instead of knowing them?
7. **Socket location:** keep `$XDG_RUNTIME_DIR/vtt/<pid>.sock` (108-byte limit) or add a
   `VTT_SOCKET` override / an abstract-namespace fallback for sandboxed agents?
8. **Docs generation:** may AGENTS.md's request tables, the README's code tables and the
   agent prompt be generated from source (R1), with a test that the committed text matches,
   or must every doc stay hand-written prose?
9. **Design records:** may their "As built" facts be moved into CODEMAP/README and the
   records frozen (R6), given the index already says they are not where to learn the present?
10. **Which invariants may become lint** (R7) and run under `make test`, given "no build tool
    beyond make and tools/"?
