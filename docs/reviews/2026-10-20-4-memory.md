# Review 4: memory -- how vtt allocates, whether leaks can be told, and the tools to tell them (vtt 2.0 input)

Reviewer: Senior Systems Engineer, memory management in long-running C (Fable 5.1). Date:
2026-10-20. Branch `vtt-2.0`, commit **d66b883** (a detached worktree checkout of it). Read-only:
every build and run was made in a `scratch/` directory inside the worktree (deleted at the end,
this report excepted) and under its own `XDG_DATA_HOME`/`XDG_RUNTIME_DIR`/`XDG_CONFIG_HOME` with
`VTT_SECRET_TOOL` empty and `VTT_CLAUDE_CURL` pointing at nothing; the one live vtt I drove ran
on a pty I opened and ended by its own `q`. Reviews 1-3 of 2026-10-12 were read first; their
claims I lean on are marked **checked**. The user's request: "a full review of how we are
handling memory allocations and opportunities of improving it. We should be able to tell if we
have memory leaks, any tools that can be added to that end should be considered."

Machine: Intel Core i7-8700K @ 3.70GHz (6 cores, 12 threads, 4.7 GHz max, powersave governor),
16 GB RAM, Samsung SSD 860 EVO 1TB (btrfs), Linux 7.2.8-9-omarchy, gcc 16.2.1 -O2 -- the
**desktop** of PERFORMANCE.md. The machine was shared and **no timing is claimed anywhere
below**; allocation counts, bytes and RSS are exact for the run that produced them.

Each finding says **reproduced** (a command run, with its output), **read** (code at
`file:line`) or **inferred** (and from what).

## Summary

- **No leak was found.** LeakSanitizer, in the sanitizer build of `./vtt`, reported nothing over
  the oracle's ~400 commands, 72 bench scenarios (every row of `tools/perf.sh` I could stage, at
  3 loops), 27 map-lifetime sequences (`:e`, discard, `:w`/`:q`, a link trip, floors, scenes, the
  menu, an agent started, the card editor), 11 tool and `--apply` runs, and a live channel over
  its real socket with 14 clients and the server's normal exit (**reproduced**, section 2).
  Ownership is regular: every allocation has a freeing path I could name (section 1).
- **Two of the leak detectors in place cannot fail where the risk is**: the release `./vtt` that
  `tools/oracle.sh` and the `--apply`/channel tests run has no LeakSanitizer (a seeded 4,321-byte
  leak passed `oracle.sh check` and `make test`'s end), and the 15 test children that end in
  `_exit` are never leak-checked (the same leak in `ctl_client_main` passed `run-tests ctllive`;
  one `__lsan_do_leak_check()` before the `_exit` made it fail). Both **reproduced** (M5, M6).
- **The frame and key paths allocate nothing**, still: over 100 loops of the build walk and 200
  of a mixed play session (fog sight, carry, roll, clock, whisper, ping, four phones) every extra
  allocation traced to the bench's own report (`stats_of`, `prof_report`) or the exit path
  (**reproduced**, M9). Allocation follows the work: a request, a save, a reload, a report.
- **Growth that is not a leak has one wrong bound.** The undo log's cap counts ops
  (`UNDO_MAX_OPS`, 1,048,576) and the header says "a little over 20 MB at the very worst"
  (`undo.h:49-50`); but a token op carries one or two 256-byte slots in the side array, so 1,500
  scene restores of 500 creatures took RSS to **287 MB**, and the cap allows about 530 MB
  (**reproduced**, M1). HEALTH 44's change sets measure 2.7 MB a waiting whole-map proposal,
  49 MB at sixteen (**reproduced**, M10). Everything else is bounded by a constant.
- **One key is a memory spike on the worst-case map**: `:check` on the walled 512x512 (a
  finding a square) allocates **534 MB** and holds **227 MB** for a 20 MB report, because each of
  the 262,145 `Finding`s is 400 bytes with its message inline and the array doubles
  (**reproduced**, M2). Real maps have a few findings; the speed of light is about 30 MB.
- **Per-request transients are 4-6x their answer** (`dump` of 512x512: 3.16 MB for 530 KB; `:w`
  of a full 512x512: 2.9 MB for 789 KB; an outside change: 2.3 MB), the `open_memstream`
  doubling plus a second copy of the answer (**reproduced**, M3; B9 and B12 already open).
- **Tools** (section 6): run the oracle over a sanitizer `vtt` too; a `child_exit` in the test
  harness that leak-checks before `_exit`; an allocation counter in `xmalloc` printed by the bench
  and asserted zero over frames and keys in `make test`; `ru_maxrss` in the bench report and a
  PERFORMANCE.md column; a `make soak` with RSS bounds. Each is shown failing once on a seeded
  fault, or how it would.

Findings: **0 high, 5 medium (M1, M2, M5, M6, M10), 5 low (M3, M4, M7, M8, M11)**, and one
confirmation (M9). M10 is HEALTH 44, measured; M3 overlaps HEALTH B9 and B12.

How I measured (so it can be redone; the scripts are described, not kept):
- **Leaks**: `make debug` (`-fsanitize=address,undefined`, LeakSanitizer on by default on Linux)
  gives a sanitizer `./vtt`; I kept a copy as `vtt-asan` and rebuilt the release. Every run of it
  is a normal exit, so LSan runs; its report, if any, is on stderr and was grepped for
  `Sanitizer`/`runtime error`. `tools/oracle.sh check vtt-asan` compares its output and exit
  codes to the record, so a report there is a diff.
- **Counts and bytes**: an `LD_PRELOAD` shim (`mcount.c`, ~100 lines: `malloc`/`calloc`/
  `realloc`/`free` through `__libc_*`, `malloc_usable_size` for bytes, requested-bytes high-water,
  and a `backtrace()` for every allocation past a count given in the environment) on the
  **release** `./vtt`, run at 1 loop and at 1+N loops of each `--bench` scenario; the difference
  over N is the steady state's cost a loop (a loop is the script's keys, each a frame, plus the
  request if `--bench-ctl`). The shim reports only from a process named `vtt` (the shell and
  `timeout` that start it inherit it). Backtraces were resolved with `addr2line` on `./vtt`.
- **RSS**: a `wait4` runner (`rss.c`) sampling `/proc/PID/status` `VmRSS`/`VmHWM` every 250 ms
  and printing `ru_maxrss` at the end.
- **Seeded faults**: a copy of `src/ tests/ tools/ Makefile` with one `malloc(4321)` added, built
  the same way, run through the same detectors.
- Fixtures: `tools/genmap.sh`'s maps (perf.sh's names), `tests/fixtures/*.vtt`, perf.sh's request
  files copied by hand, the void 100x60 and 512x512 maps.

### M1 (Medium): the undo log is capped in ops, and a token op is 13-26 ops' worth of bytes

**Read.** `undo.h:44-55`: "The cap is four fills of the largest map (512x512 is 262,144 ops a
fill), a little over 20 MB at the very worst"; `UNDO_MAX_OPS (4 * MAP_MAX_DIM * MAP_MAX_DIM)`.
`trim` (`undo.c:56-80`) drops batches until `nops` is under `UNDO_TRIM_TO`; nothing looks at
`ntoks`. `push_token` (`:145-152`) appends a 256-byte `Token` per slot: an add or a delete pushes
one (`:204`, `:216`), an edit two (`:251-252`), a note, an area, a link or a roll two
(`:323-324`, `:368-369`). A cell op pushes none. So the log's bytes are 20 x ops + 256 x slots,
and at the cap with two slots an op that is 20 MB + 537 MB (`toks` doubles: 1,048,576 x 256 =
268 MB of capacity at 786,432 slots).

**Reproduced.** `horde.vtt` (60x40, 500 creatures), `--bench` of `:play\r:scene save A\r:scene
A\r` x 1,500 (a restore deletes and re-adds each creature, `scene.c:111-115`: 1,000 one-slot
ops): `maxrss_kb 286884`. The shim over 20 loops: `xrealloc` 130 times, 120 of them under
`scene_save` (M4) and the rest the log's doubling; 24.2 MB requested for 20 loops, 1.2 MB a loop.
Arithmetic: 1,500 x 1,000 = 1.5 M ops, trimmed to 786,432; 786,432 slots x 256 B = 201 MB in a
268 MB array, plus 21 MB of ops: 287 MB. The header's 20 MB is the cell-op case only.

Is it met in play? A fight's counters (`<>`, `:dmg`) are edits at 532 B each: 10,000 presses are
5.3 MB. Scenes, summons and damage over hundreds of creatures are what reach it. The practical
harm is RSS (the `:ask` fork's cost grows with it, review 2 B12) and that the invariant written
in the header is false. **Fix**: cap the log in bytes (`nops * sizeof(Op) + ntoks * sizeof(Token)`
against a limit near the 20 MB the header promises, or 64 MB), trimming by batches until under
it -- the same `trim`, one more condition; HEALTH 90's ring (D16) makes the trim O(1) either
way. A test: push 100,000 two-slot ops, assert the bytes.

### M10 (Medium, HEALTH 44, measured): a waiting whole-map proposal is 2.7 MB; sixteen are 49 MB

**Reproduced** as in the table. The row's estimate ("about 6 MB a fill, 16 of them about 100
MB") was high by two: a `CsCell` is 8 bytes (`changeset.h:28-33`) and the index is a 32x32 block
table. The cap the row asks for (cells across all waiting jobs, with the refusal an agent is
told) stands; a number: 4 M cells (32 MB) refuses the 13th whole-map fill and never a plan of

## 6. Tools

Within the rules (no dependency the build needs; a tool is a make target or a file in `tools/`).
For each: what it catches that nothing catches now, its cost, and how it fails once on a seeded
fault.

### T1. Run the oracle, and the tests that run `./vtt`, against a sanitizer `vtt` too (M6)

**Catches**: a leak, an overflow or a UB in any path the oracle drives (`--check`, `--describe`,
`--dump-map`, `--script`, `--apply`, the request corpus, the generated maps) -- paths the unit
tests reach only partly (review 3: `ctl.c` 47%, `main.c` 0%). Today the release binary runs
there and a leak passes (**reproduced**: seed in `run_tool`, `oracle: the same`).

**Cost**: a second compile of `src/*.c` with `DBGFLAGS` into an object dir of its own
(`build/asan/`; the Makefile's mode stamp wipes `build/*.o` when the mode changes, so the two
cannot share `build/`), linked as `build/vtt-asan`; then `tools/oracle.sh check build/vtt-asan`
after the release one. Wall time, one run each on the shared machine (rough): the oracle took **27 s over the
sanitizer `vtt` against 6 s over the release one**, so about 20 s more, plus the compile
(review 3 timed the one-`cc` test build at about 50 s; a second full compile is of that order
unless the objects are shared with `run-tests`, which `test-build` does not build from objects
today). `make test-fast` may keep the release oracle only.

**Fails once**: the seeded `run_tool` leak above -- `oracle(asan) exit=1` with the LeakSanitizer
report in the diff. A report's text carries addresses, so the check should be the exit code and
`grep -c Sanitizer` rather than the record (or `ASAN_OPTIONS=exitcode=23` and `-- exit 23` in the
record is enough: the exit line is what differs).

### T2. `child_exit()` in the test harness: leak-check before `_exit` (M5)

**Catches**: leaks in `ctl_client_main`, `ctl_apply_open`, the `--apply` and disk children --
15 sites in `tests/`, the whole client half of the channel. **Cost**: `#include
<sanitizer/lsan_interface.h>` under `#if defined(__SANITIZE_ADDRESS__)` (gcc and clang both
define it), one function in `harness.c` (`__lsan_do_leak_check(); _exit(rc);`), 15 call sites
edited; milliseconds a child. **Fails once**: **reproduced** -- the seeded `ctl_client_main`
leak passed without it (203 checks, 0 failures) and failed with it (`FAIL test_ctl.c:1450`,
`ctllive FAILED`), the child's report in its captured output. The same helper is where review
3's gcov hole closes (`__gcov_dump()` before `_exit`).

### T3. An allocation counter in `xmalloc`, printed by the bench, asserted in `make test`

**Catches**: a `malloc` creeping into the frame or key path -- the one invariant of M9 that
nothing tests (V2.md asked for it at step 2 and it was not built). **Design**: a global
`unsigned long alloc_calls` incremented in `xmalloc`/`xcalloc`/`xrealloc` (one add; the frame
path has none, so the cost is nothing there), read by `--bench` which prints `allocs: N over the
loops` (the count between the first loop's end and the last's, so setup is out) and by perf.sh
into a new column; and a case in suite `loop` (which already drives `loop_once` through a pipe)
that replays a build walk and a play walk for 100 frames and asserts the counter unchanged. The
17 raw `malloc` sites are outside the frame path (the channel's client, accept, `stamp_show`, the
trace); the counter would miss one only if a new raw site were added to a frame -- a rule for
CODEMAP: "a frame or key path allocates through `xmalloc`, and the counter says so". Exactness
beyond that (every libc allocation) is the shim's job (T5). **Fails once**: add `xmalloc(1)` to
`app_draw`; the case fails on the first frame. I did not build this (tracked files); the
assertion is direct.

### T4. `ru_maxrss` in the bench report and PERFORMANCE.md

**Catches**: a key or request whose peak memory is out of proportion -- M2's 227 MB and M1's 287
MB would each have been a row. **Cost**: `getrusage(RUSAGE_SELF)` once at the end of `--bench`
(`getrusage` is POSIX; `ru_maxrss` is a Linux and BSD field), printed as `maxrss KB`, a column in
perf.sh's table; nothing on any path. **Fails once**: it is a measurement, not a check; the check
is T6's bound.

### T5. `tools/mcount.c` and `tools/rss.c` (or one `tools/mem.sh`), kept as developer tools

The shim and the runner of this review, under `tools/`, with a `make alloc-count SCENARIO=...`
target that compiles the shim on demand (no build dependency; glibc's `__libc_malloc` and
`malloc_usable_size`, so Linux/glibc only, said in the header) and prints calls, bytes and
live-max a loop with backtraces past a count. **Catches**: where an allocation comes from, which
the counter (T3) cannot say. The house rule: a tool worth a second use becomes permanent; this
one found M1, M2, M4 and M9 in an afternoon.

### T6. `make soak`: long scripted sessions with RSS bounds

**Catches**: growth with session length that no single test sees -- M1 would have failed a
bound. **Design**: `tools/soak.sh`, the runs of section 3 (the mixed session x 10,000, 28 fills,
1,500 scene restores, 20 fill proposals, 50 dumps, 300 events) under the `rss` runner, each with
a bound (mixed 8 MB, fills 40 MB, scenes 40 MB once M1 is fixed, proposals 60 MB, dumps 10 MB,
events 8 MB), failing on `ru_maxrss` over it. **Cost**: a minute or two of wall time; not in
`make test` (perf wants the machine; this does not, but it is long). **Fails once**: the scenes
row fails today (287 MB), which is the point; and any bound set under a measured value fails.

### T7. Optional, not installed here: valgrind massif, heaptrack

Neither is on this machine (`which`: none). `valgrind --tool=massif ./vtt map --bench keys` gives
the heap's peak by call site (M2's picture in one run); heaptrack the same with less slowdown.
Developer tools, named in CODEMAP's conventions, no target.

### Not recommended

- `mallinfo2`/`malloc_usable_size` in the program for live-bytes accounting: glibc extensions,
  not POSIX; `ru_maxrss` (T4) and the counter (T3) cover what is needed without them.
- `__lsan_do_recoverable_leak_check` inside the loop: LSan stops the world and walks the heap;
  not for a frame.

### A gotcha met on the way (M11, Low)

A sandbox whose `XDG_RUNTIME_DIR` is under a deep path (my scratch tree: 100+ characters) makes
the channel refuse to start -- `the socket path is too long` (`ctl.c:80-108`, the 107-byte
`sun_path`) -- and a script then runs with the channel off and may not notice (my first live run
answered every request with "the agent channel is off"; the oracle and the harness use short
`/tmp` paths, so the suite is fine). **Reproduced**. The note belongs in tests/CLAUDE.md's
sandbox paragraph: keep the runtime dir short.

### M5 (Medium), M6 (Medium): as above, under T2 and T1.

### M7 (Low): four `open_memstream` sites do not check for NULL

**Read.** `apiagent.c:176`, `:193`, `:438` and `app_agent.c:343` use the `FILE *` at once;
`open_memstream` fails only for ENOMEM, where the program's rule is `die` (`xmalloc`). The other
seven sites check (`app_agent.c:258`, `app_event.c:73`, `app.c:506`, `app_cmd.c:1022`,
`mapio.c:188`, `request.c:1427`, `:1821`). An `xmemstream(&buf, &len)` in `util.c` that dies
makes it one rule and one line each.

### M8 (Low): two conventions for OOM, and a trace buffer kept

**Read.** `xmalloc` dies; the 17 raw sites fail soft (section 1). Both are defensible -- the
client and the channel prefer to close a connection over killing the GM -- but CODEMAP's `util.c`
row should say which modules may use raw `malloc` and why, or the rule "allocate through
`xmalloc`" is false in four files. `prof.c:311` mallocs 200,000 x 24 B = 4.8 MB at `--trace` and
`prof_trace_close` writes the file without freeing it (reachable static; a developer flag);
`free(P.trace)` there costs nothing.

## 7. Recommendations, in order

1. **Make the leak detectors able to fail** (M5, M6; T1, T2): `child_exit()` in the harness at
   the 15 `_exit` sites, and a sanitizer `vtt` run through `tools/oracle.sh` at the end of `make
   test`. Both proven on seeded faults above. Until then "make test is LSan-clean" says nothing
   about the client half of the channel or about `main.c`.
2. **Cap the undo log in bytes** (M1): one condition in `trim`, the header's "20 MB" made true
   (or raised and made true), a test with two-slot ops. Then HEALTH 90's ring as planned.
3. **`ru_maxrss` in the bench and PERFORMANCE.md** (T4), and **`make soak`** (T6) with the
   bounds above: the measurement that would have shown M1 and M2 as rows.
4. **The allocation counter** (T3): `xmalloc` counts, the bench prints, suite `loop` asserts zero
   over frames and keys. V2.md's step-2 debt closed; the M9 invariant tested rather than claimed.
5. **`Finding` out of line** (M2) when `maptools.c` is next touched: the message formatted late
   or kept apart; the array sized once. Not before.
6. **HEALTH 44's cap** (M10) with a number: 4 M cells across waiting jobs, the refusal an agent is
   told; and B9/B12 as they stand.
7. **Small**: `tokens_reserve` in `scene_save` (M4); `xmemstream` (M7); `free(P.trace)` and a
   CODEMAP line on raw `malloc` (M8); the sandbox note (M11).
8. **Keep** `mcount.c`/`rss.c` in `tools/` (T5) so the next memory question is a command, not a
   review.

### Open questions for the maintainer

1. The undo log's bound: 20 MB as the header says (so about 70,000 two-slot ops -- 140 scene
   restores of 500), or larger with the header changed? A bytes cap changes when a long session
   loses its oldest history.
2. Should `:check` refuse, or fold, past some number of findings (10,000?) rather than build a
   262,145-line report nobody reads? That removes M2 without touching `Finding`.
3. Is the sanitizer oracle for `make test` (about a minute more) or for `make test` before a
   commit only, with `make test-fast` keeping the release one?
4. Raw `malloc` in `ctl.c`/`request.c`/`stamp.c`: keep the fail-soft convention (and say so in
   CODEMAP), or move to `xmalloc` and accept that an OOM at accept kills the GM's vtt?
5. `ru_maxrss` as a PERFORMANCE.md column: publish the median of three like the times, or the
   max (memory peaks do not jitter the way times do)?
