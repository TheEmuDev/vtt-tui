## What the reviews say, in one paragraph

The leaves are good and the spine is not. The renderer, the wire to the phones, fog and
sight, the undo op, the change set and the proposal model were each measured or read and
found at or near the floor; the reviewers ask that they be carried over unchanged. What they
ask to be rebuilt is everything those leaves hang from: the loop (`main.c`, untested, and
blocking on the terminal), the 200-declaration `App`, the channel's protocol (prose where
codes should be, a grammar kept in six hand-written lists), the file's density, and the
absence of any seam a test can put a fault through. So "full rewrite" has two readings, and
the first decision below is which.

## Decisions

Each gives the choice, the road not taken and what it costs.

**D1. The shape of the rewrite: rebuild the spine, carry the leaves.** *(the user's to
confirm, question 1)* A new `src/` is laid down in the order of *Build order*; the pure
modules (`map`, `fog`, `sight`, `undo`, `changeset`, `checkpoint`, `ruler`, `wire`, `json`,
`render`, `grid`, `dice`, `card`) move in with their tests, changed only where a decision
below names them; everything `app_*`, `main`, `ctl`, `net`'s service loop, `term` and `mapio`'s
writer is written again against the new structure. The other road is a clean room: every
line rewritten. It costs about 35 KLOC and the 19,173 checks to reach where the leaves
already are, and three reviewers found nothing in those files to fix. It buys a uniform
style and nothing measurable.

**D2. `World`, and a loop that is a function.** `App` splits along the seams its own
comments draw: `World` (map, undo, jobs, events; as built, also the tick's clock and the
state of the request being run, and not the overlay, which is the editor's) is what a
request handler takes; `Channel`, `Net`, `Disk`, `Editor` and `Play` hold the rest. The
loop's body becomes `loop_once(App *, const Ready *, uint64_t now_ms)`, `Ready` being what
`poll` said; `main` builds it from `poll`, a test builds it by hand. *(As built: `loop_once(Loop *, int nready, now_ms)`, the descriptors inside `Loop` and filled by `loop_wait`, so `Ready` is poll's own `revents`.)* No run-time cost. Not
taken: sub-structs alone (review 3: necessary, not sufficient, since handlers would still
take `App *`).

### The `World` move: the plan (2026-10-13; signed off by the user the same day, with decision 2 changed)

What F13 asks: a request handler takes the whole `App`, so every protocol test is an
application test with a renderer, an editor and a terminal's worth of state behind it.
D2's answer is `World`. This is how it is cut, in what order, and what it costs.

**What a handler reads today** (counted, `a->FIELD` in `app_ctl.c`, `app_ctl_job.c`,
`app_event.c` and the half of `app_job.c` that is not the review's keys and drawing):
the map and its log (`map`, `undo`: 68 uses), the jobs (`jobs`, `job_last`), the event ring
and the checkpoint's marks (`events`, `event_seq`, `cp_gen`, `cp_off_*`, `seen_gen`,
`change_ms`, `agent_seen_ms`), the request's own state (`ctl_who`, `ctl_auto`,
`ctl_direct`, `ctl_can_hold`, `ctl_held`, `ctl_hold_*`, `ctl_refused`, `ctl_scratch`,
`ctl_sundo`, `agent_on`, `now_ms`): that is `World`. And eleven things that are the
GM's side, reached through `app_*` calls 28 times in all: a line on the GM's status and
in the log; whether the GM is busy (`app_ctl_busy`: screen, modal, mode, a key half
typed); what a landing does to the screen (the selection, the range, the frame); the
screen's lines of `status`; `marked`; the ring round a change; the job under review;
starting the GM's agent command.

**Decision 1: `World` is a struct, and the GM's side is a `WorldHost` of function
pointers.** `World` holds the fields above and a `const WorldHost *host` with its
context: `note(ctx, text, logged)`, `busy(ctx)`, `landed(ctx, what)`, `screen_lines(ctx,
out)`, `marked(ctx, out, json)`, `ring(ctx, box)`, `reviewing(ctx)`, `review_leave(ctx)`,
`agent_start(ctx, job)`. The app is the one real implementation; a test supplies
small functions that record what they were asked. *(As built the list is fifteen, in
`world.h`: step 2's `note`, `busy`, `landed`, `reviewing`, `review_leave`, `job_gone`,
`deaf`, and step 3's `redraw`, `changed`, `ring`, `screen_lines`, `marked`, `floor_shown`,
`refused`, `heard`; `agent_start` was not needed, since no handler starts an agent.)* This is D3's shape (a seam is a struct
of function pointers with one real implementation), used for the seam D2 needs. Not
taken: handlers calling `app_*` by name with a second set linked for tests (one test
binary cannot hold both); `World` holding a pointer back to `App` (then a handler can
reach anything again, and F13 is not answered).

**Decision 2: the plain rename** *(as ruled 2026-10-13: this branch is merged into `main`
when it has been tested and played, and nothing of `main` comes back into it, so there is no
later merge for a mechanical diff to collide with)*. The fields move into `World`, the
`App` holds it by value as `world`, and every use says so (`a->world.map`): 1,700 uses
changed by script, the compiler naming each one missed and each one changed wrongly, since
no other type has a `world`. First planned and not taken: an anonymous struct in `App` over
the same fields, so that `a->map` and the new spelling were one object, which spared the
diff and left two spellings for one field. The member is `world` and not `w`, which is a
width everywhere else here.

**Decision 3: three files move, and each keeps a wrapper where the app and the tests call
it.** `world.h` (the struct, the host); `world.c` (the event ring from `app_event.c`; the
jobs' core from `app_job.c`: new, clear, thread, the proposal's seam, `land`, the
result); `request.c` and `request_job.c` (`app_ctl.c`'s and `app_ctl_job.c`'s handlers and
`world_exec(World *, req, &len)`). What stays the app's: `app_ctl_busy`, `marked`
(`app_ctl_marked.c`), `:agent`, the review's keys and drawing, the held waits' flush
(the socket is `Ctl`'s, not the world's), the agent command. *(As built, after decision 2 became the plain
rename: no wrappers. The functions are `world_*` and `request_*` at every caller.)*

**Performance considerations.** No path gains or loses work. Per path:

| path | speed of light | today | this design | gap |
|---|---|---|---|---|

| a note to the GM, a busy check, a landing's screen work (per request, never per frame) | the call | a direct call | an indirect call through `host`: about 1 ns more, some 3 a request | 3 ns a request against 20 µs and up |

**D3. Five seams, each a struct of function pointers with one real implementation.**
`Clock` (already passed in; made total: no `clock_gettime` outside `main` and `prof`),
`Sink` (the terminal), `Conn` (channel and phones), `Spawner`, `Disk`. Cost: one indirect
call per syscall, nanoseconds beside the syscall. Not taken: `LD_PRELOAD` shims in tests,
which test the libc boundary and not the program's decisions.

**D4. The terminal is a non-blocking sink with a pending buffer.** *(As built: the tty is
opened again by `ttyname` of stdout, not `/dev/tty`, which is the controlling terminal and
need not be the one vtt is drawing on; and a frame drawn while bytes are pending is dropped
whole and redrawn when they have gone, rather than diffed against a delivered front.)*
Output is its own open of `/dev/tty` (`O_WRONLY | O_NONBLOCK`), which is the only way round the shared description
`term.c:84-89` describes. The frame's bytes go to a pending buffer; the fd joins `poll` for
`POLLOUT` only while bytes are pending; a frame drawn while the last is still going out is
diffed against the last *delivered* front. Tradeoff: the renderer's "front is what the
terminal shows" becomes a statement about delivered bytes, and that is where a bug would
hide, so it gets a property test over random short writes. Fallback when `/dev/tty` cannot
be opened (output piped): today's blocking write.

**D5. Requests are budgeted.** A turn spends at most a fixed slice (2 ms proposed) on
requests, then handles keys and draws; what is left runs next turn. `REQUESTS[]` carries a
cost class, so the dispatcher knows a read from an edit. A read is never split across turns
(a split read needs a snapshot); instead D7 bounds what one read can cost.

*The budget, as built (2026-10-13).* Two bounds, since a request is never cut short. **A
turn's slice:** `app_tick` runs ready requests until `CTL_TURN_NS` (2 ms) is spent, always at
least one, and leaves the rest ready; `ctl_due` is then 0, so the next turn comes at once,
after this one's keys and frame. Four requests that arrive together are four turns with the
GM's keys between, where they were one turn of all four. **A request's own bound** is not a
time, which would refuse the same request on a slow machine and take it on a fast one: it is
the squares of map its reads walk (`CTL_READ_SQUARES`, 300,000: one whole read of the
largest map and some regions). A `dump` counts its region; `describe`, `check` and a job
read back count the map. Past it the request is refused whole, `limit`, as any line's
failure refuses it. The review found the reads were half of it: an edit that changes nothing
records nothing, so the cap on recorded changes never saw 3,200 lines of `tile A1:SR512
floor`, three seconds of one turn. **An edit counts the squares it covers**
(`CTL_EDIT_SQUARES`, the largest map twice: a fill its region, a wall its outline, a room its
box, a stamp its size, a corridor its legs), and a file read from the GM's stamps or
characters counts as squares read (`CTL_FILE_CHARGE` each; a listing, which opens all of
them, a third of the request's reads). Measured after (2026-10-13; PERFORMANCE.md, *Reads that cost what
was asked*): `help` written 12,800 times in one request was 43 ms and tens of megabytes, so
**once an answer has passed 2 MB no further line is run** (`CTL_ANSWER_CAP`; a single line's
answer is never refused for its size: a crowded map dumped whole was counted at 2.7 MB and
is what was asked). `changes` is asked three times a request at most; `holds`, `job N say`
and `scene diff` are charged for the stat, the log's line and the creatures compared. And
one whole `describe` or `check` of the largest map was a request of 10.9 and 9.2 ms at the
median where `dump all` is 5.3; since 2026-10-13 they are 3.7 and 3.2 (HEALTH 70, closed:
the room finder read the map through a million bounds-checked calls), so "one whole read"
is the dump's 5.5 ms of a turn at most. `--apply` on a file is not bounded: nobody waits on a frame
there. `changes` never refuses for it: what it may not read it lists under `more:`.
Departure: `REQUESTS[]` carries no cost class. The slice is measured, not predicted, and
the count is taken where the read is made, since `describe B2` and `dump B2` share a verb's
shape and not its cost.

**D6. One `REQUESTS[]` table and stable codes.** The table holds name, kind, where it is
allowed, argument shapes, cost class, a one-line doc and the handler; `is_edit`, `off_takes`,
`lonely`, `not_alone` and the 320-line chain become lookups, `help [VERB]` is printed from
it, and a test asserts AGENTS.md lists exactly its verbs. The verdict line gains a code
(`error R301 line 3: ...`) and so does each event; `--wait` matches codes. Text stays the
wire's default and JSON stays opt-in (review 2: JSON is 2.0 to 2.3 times the bytes).

*The codes, as built (2026-10-12).* A code is a **word, not a number**, and there is one per
*thing the caller should do next*, not one per error site: about 150 sites share six
classes, because a code is worth its tokens only where it changes the agent's next request,
and the sentence after it already says which square or which name. The verdict line is
`error CLASS: line N: the sentence` (`busy: ...` and `ok` are as they were):

| class | the caller's next move | examples |
|---|---|---|
| `usage` | the line is wrong as written: `help VERB`, write it again | unknown verb, a word too many, `Z99` on a 40x30 map |
| `missing` | a name in it names nothing: list them (`jobs`, `scenes`, `describe`) | no job #7, no creature called Orc |
| `conflict` | what is there is in the way: look (`dump REGION`), choose other squares or another name | a square taken, a room over another, a label in use, a box off the map |
| `state` | nothing is wrong with the line; not now, or not yours: read `status` and `jobs` | the channel off, no map open, a job the GM is deciding, nothing to undo |
| `limit` | over a fixed size: split it or shrink it | a request over 64 KB, a line over 1023 characters, sixteen proposals waiting |
| `internal` | vtt's own failure: say so to the GM | out of memory |

`usage` is the default, so a site says its class only when it is another; a refusal that
comes up from a module below the channel (`corridor_plan`, `stamp_place`) is classed where
the channel calls it. An event's code is the word after its subject, ended by a colon or the
line: `SEQ job N KIND[: text]` or `SEQ map KIND: text`, with `asked`, `accepted`, `part`,
`feedback`, `scrapped`, `removed`, `back`, `changed`, `closed`. Emitters and `--wait` take
the words from one table (`ctl.h`), which closes HEALTH 16. Tradeoff: six classes cannot
tell "no such job" from "no such scene"; the sentence does, and a finer code would be a
second vocabulary to keep true. Speed of light: a class is one word in a verdict that is
already a line; nothing is looked up.

**D7. Reads cost what was asked.** `status` prints `seq`; `wait 0` with nothing kept answers
at once; `changes SEQ [REGION]` prints the change sets kept in the event ring up to a byte
budget, saying `lost` past it, and is never built by diffing two maps; a `dump` with no
region above a square count answers with the bounds and a hint unless `dump all`; the key
moves behind `dump key`; `describe` takes a region or a filter.

*The reads, as built (2026-10-12).* `dump` takes `REGION`, `all` or `key`; with none it is
the whole map up to 4,096 squares (`CTL_DUMP_SQUARES`, about 16 KB) and a `limit` refusal
past that, which names the map's corners; a job's `dump` is held to the same. `describe`
takes a region: the rooms that meet it, each whole, with a line saying how many of how many.
`changes SEQ [REGION]` prints the events after `SEQ` and then, for each region they
changed, `changed REGION` and its dump as the map is **now**. What an event keeps is not
its change set but where the change was: a bit a piece of the map cut sixteen by sixteen
(`CsWhere`, 32 bytes; a piece is at most 32×32 squares), marked when the event is made from
the set it already had in hand. Runs of pieces are sent as one region, never grown past
half an answer (`CTL_CHANGES_BYTES`, 16 KB), and what does not fit is a `more:` line of
regions to `dump`. Departures from the sentence above: there is no *before* in the answer
(an agent acts on what the map is, and the event's line already says what happened), and
the regions are coarse, a change and some squares round it. An 8×8 grid was tried first:
on a 512×512 map one piece was more than an answer. Events older than the ring say `lost`,
and then nobody knows where; so does a `map closed` among them. The review found the hole
under all of it: the checkpoint stops when no agent has been about for ten minutes, so a
change then was no event and `changes` said nothing; an agent coming back is now told
first, in one event with every piece. A region's real bytes decide whether it is sent (the
lattice is the least of a region full of creatures), and the 16 KB is `changes`' own. Not built: a filter for `describe` other than a region.

**D8. An agent has a name, and an accepted job is undone by number.** *(as ruled, question
6)* A request may open with the line `agent NAME`; `vtt --ctl` writes it from `VTT_AGENT`
when that is set, so an agent never types it, and vtt sets `VTT_AGENT=job-N` beside
`VTT_JOB` for an agent it starts. No name is the name `cli`: reads and proposals are taken,
and `take`, `drop`, `propose` and `undo` on another name's job are refused with a code, so a
mistyped name fails shut instead of being credited to someone else. A job records its
taker; `job N undo` undoes an accepted job by number and plain `undo` means the caller's own
last one; `job N conflicts` lists what `cs_check` already knows; each landing stamps its
undo mark with name and job. `status` prints the caller's name as vtt saw it, beside `seq`.
**Waits are held one a name:** a second `wait` from a name answers the first (its `seq`,
code "superseded") and is held in its place, so an agent that is killed and tries again can
never lock itself out, and one agent's repeats cannot take every slot as they can today
(`ctl_hold`, `ctl.c:333`). Callers with no name share one slot. **vtt becomes the parent of
the agents it starts:** the double fork (`app_agent.c:126-130`) goes, the loop reaps with

*Names, as built: the first part (2026-10-13).* A request's first line may be `agent NAME`;

*Names, as built: the second part (2026-10-13).* **A landing says whose it is, on the undo

**D9. Sparse rows in a new file version, and the flush off the key.** *(as ruled, question
2; as built in step 5: version 14, not a new one; an empty line, not a run; the flush stays
on the key. See *Step 5, the file format*.)* A row that is all void is written as a run. 2.0 writes one version, the newest, always:
the rule that the writer picks the lowest version that says everything is dropped, since
nothing needs 1.x to read what 2.0 saved, and with it go the writer's fourteen branches. The
loader keeps all fourteen. The oracle for files is therefore the *loaded map* (each old
fixture read by both binaries and compared through `--describe` and `--dump-map`), and
2.0's own round trip (save, load, save: the same bytes), not 1.x's bytes. A save on a key is
`write` and `rename`; the `fsync` runs after the frame, and on close and quit. Tradeoff: a
power cut inside that turn can lose the save the GM just asked for (the file is intact
either way, old or new). Question 3.

### Step 5, the file format: the plan (2026-10-13, revised the same day after its review; signed off by the user the same day, "go with the recommendations"; built, see *Progress*)

The first draft had three parts: one version written always (15), a new line `*N` for N
rows of nothing, and the flush moved after the key's frame with the order changed to
write, frame, flush, rename. A Fable review of the plan against the code changed two of
the three, and its checks were run again here. What is proposed now:

**Part 1: one version, always, and it is 14.** `write_map` works out the lowest of
fourteen versions that can say the map (twenty lines of flags and one eleven-way
conditional). 2.0 writes `VTT 14`, the newest there is, every time; the flags go. The
loader uses the number for one thing, refusing a file newer than itself (`mapio.c:985`,
the only read of it), so a map with no cards and no fog loads to the same map whatever
number heads it. Because part 2 needs no new syntax there is no version 15: a 1.x vtt of
the last release still opens what 2.0 saves. What changes in the tree: the tests that
assert a *lower* number for a plain map encode the dropped rule and go; those that read
the head of a saved file expect 14; CLAUDE.md's invariant, mapio.c's header comment, the
CODEMAP row and the README's *Versions* paragraph say "one version, the newest".

**Part 2: a row of nothing is an empty line.** Not `*N`. The loader already reads a short
row as padded with nothing and an empty line as a row of nothing (README, *File format*:
"short rows are read as if padded with spaces"; checked: a file whose rows are empty lines
dumps as the right map), and trailing spaces trimmed by an editor, and CRLF. So the writer
writes an empty line for a row that holds nothing *as written* (void; no edge; a fog row
all `.`, which is what lit squares and dead patches are written as: the test is of the
characters, not the bytes), and every other row whole, as now. An empty 512×512 map is
789 KB today and about 2 KB then; a line of the file is still a row of the map in an
editor; nothing new for the loader to forgive. The one loader change: an empty line in a
row section is no longer counted "short" (`N021`), or every map 2.0 saves would carry
three notes in `--check`. Not taken: `*N` (60 bytes against 2 KB, both one page and one
write, for a new syntax, a new diagnostic and line numbers that stop being rows);
trimming the trailing nothing off part-empty rows (it would cut a dungeon in the corner
of a big canvas tenfold again, but a trimmed `vedges` row is what `W022` exists to flag
as a missing east wall; that warning has caught real hand-written maps, so rows that hold
anything stay whole).

**Part 3: the flush stays on the key. D9's deferral is dropped.** Three findings, the
first the planner's own: (a) D9's order, rename on the key and flush after the frame, can
leave an empty file under the map's name after a power cut on some file systems; (b) the
safe order (write, frame, flush, rename) splits `mapio_save` across a turn, and five
things that today follow it at once must move with the second half (the autosave's
removal, the map's path, its unsaved mark, its base and identity, the outside-change
state), with the status line saying "wrote" for a turn before it is true; (c) and it buys
one frame: the loop has one thread, so the next key waits for the flush wherever it is
put. On this desktop that is 2.0 ms at the median; on the laptop 33 to 67 ms, where the
real help is part 2 (4 KB flushes in half the time 789 KB does). The user ruled once
before that everything but the autosave keeps its flush (HEALTH, the first check, item 1);
this agrees with it. If a frame before the flush is ever wanted, the shape is the whole
save run after the frame (one pending flag, `mapio_save` intact, the key's frame saying
"saving"), not a save cut in two. Taken with part 1, since it is a line: the temporary
file gets a name of its own (the pid in it), so two vtts saving one map do not write
through each other's.

**Not in this step** (the build order lists them under 5): the `Disk` seam comes with the
simulation driver that needs it (step 9's fault schedule); the table-driven loader is its
own piece after this, measured against the 3.4 ns a byte it has now.

**Performance considerations.** The desktop; the laptop's flush is fifteen times dearer.

Instrumentation: `mapio.write` and `mapio.fsync` stay. New: a `:w` scenario in

**How it is tested.** (1) *Fidelity, not only stability:* every fixture, oracle map and

### Step 5, second piece: findings a GM can act on: the plan (2026-10-14, revised the same day after its review; signed off by the user 2026-10-16; part 1 built, see *Progress*)

**Why.** Step 5 made most rows of a saved map empty lines. One added or deleted by hand,
by a tool that squeezes blank lines, by a merge or by an agent that edits the file as
text instead of through the channel, moves every row below it in that section, and today
nothing says where: an added line is silent when the row it pushes out is empty (HEALTH
80), says only "rows outside any section" when it is not (W019), and a deleted one says
the section is short at the *next* header (E011), never where the line went -- and the
header it swallowed strands the whole next section, so a missing `tiles` row loads a map
with no vertical walls at all (checked). Nothing vtt does can cause it: every way vtt
changes a map goes through the one writer, which the `mapfile` suite holds to one line a
row. The user's direction (2026-10-14): a warning or error should be as useful as a good
compiler's. So this piece is two things: this one finding made exact, and a standard
every finding is held to.

**The standard: what a finding says.** Taken from what the good compilers do (rustc,
clang, Elm):
1. *Where*, as exactly as it is known: the file's line (and column when there is one),
   and for a square its name (`G5`, `G5|H5`) beside the line of the file it is on.
2. *What was read, and what vtt did with it*: the loader forgives, so every finding says
   what the map now holds because of it ("read as void", "the rows below are one lower").
3. *Why it matters*, in one line, when it is not obvious (a `note`).
4. *What to do*: a `help` line naming the fix, in vtt's own terms (a key, a command) for
   a problem on the map, in the file's terms (delete line 214) for a problem in the file
   -- and honest when the fix is not vtt's to know (a deleted row that held something
   must be restored from a copy).
5. *The evidence*, when the finding is a judgment: what vtt saw that makes it think so,
   and how sure it is ("with line 214 gone, 14 walls that stand on void stand on floor").
6. *No cascades.* One mistake, one finding: the findings it causes are folded into it
   and counted, not listed (a compiler that reports one missing brace, not two hundred
   errors after it).
7. *Quiet when unsure.* A judgment without evidence is not said at all (a blank line
   between sections is legal, and a note on every hand-written map would be noise), and a
   file vtt wrote never has a finding about its own form (the `mapfile` suite asserts it).
8. *One code, one meaning, documented*: every code in the README's table (two are
   missing today: `W030 env-dropped` and `W170 env-no-card`; checked with `comm` of the
   two lists), stable once given.

The text output keeps its first line as it is (`CODE slug where message`: what agents,
tests and the oracle read), and the rest goes on indented lines under it, as rustc does:

```
W031 row-extra          line 214  'tiles' has one row too many: rows from line 214 down are one lower than the map's walls
     |
 213 | ....|....
 214 | ....|....              <- this line repeats the one above it
 215 | ....+....
     = evidence: with line 214 gone, 14 walls that stand on void stand on floor, and the
       creature Ogre stands on floor instead of void
     = help: delete line 214; then vtt map.vtt --check
     = 15 findings are caused by it and folded (W103 x14, E110 x1)
E011 section-short      line 412  'vedges' read as tiles row 30 of 30: a 'tiles' row is missing, and 'vedges' was not read
     = evidence: the row is missing after line 395 (or anywhere in 396-399, which are the
       same empty row): above it the floor fits the walls, below it every row is one high
     = help: if the missing row held nothing, add an empty line after line 395; if it held
       something, take it from a copy (the autosave, a backup)
     = 26 findings are caused by it and folded (W019 x1, W103 x25)
```

`--json` carries the same as fields beside the ones it has: `help` (a string), `notes` (a
list of strings), `span` (first and last line, for a range), `folded` (the codes and counts
folded into it), `confidence` (`certain`, `likely`). Folded findings are not in the
`errors`/`warnings` counts nor the exit status: the finding they fold into is. The
channel's `check` and the GM's view (below) use the same text.

**Part 1: the line search.** It works on the file's *text*, not on the loaded map: a
missing row has already swallowed the next header and stranded a section, which no map
can undo (the review's check). The three row sections describe the same squares, so an
extra or missing row in one shows as a seam: above it the section fits the others, below
it every row is one off. Creatures, notes, areas and links are given by coordinates,
which a moved line does not move, so they fit the true rows.
- *The sections by their headers* (mapio.c, which owns the format): one scan of the
  file's lines finds each row section's header and the lines up to the next header or
  record, whatever the size says -- so each section's real lines are known even when the
  loader's count went wrong. A section with one line more than its rows, or one fewer, is
  a candidate; so is one whose count is right but whose last line is a blank and whose
  rows score better shifted (a blank separator swallowed as the missing row: the review's
  check 4).
- *The trigger* in the app (every open, so it must cost nothing): the line after a row
  section's last row is not a header or a record, or a section swallowed one. `--check`
  and `:check` run the search on every row section untriggered (it is about 0.3 ms), which
  also catches the count-right case above.
- *The candidates*: every line of the section (not only empty ones: a duplicated row,
  `yyp` in an editor, is the commonest accident, and its pushed-out row is what the
  trigger sees, not the line to remove), with a run of identical adjacent lines one
  candidate, since removing any of them makes the same file; for a missing row, every gap.
- *The evidence*, against the other sections as the text gives them: walls and doors with
  no map square on either side (W103, E101 as `check_map` defines them), and creatures,
  notes, areas and links standing on void. Not fog: a patch over void is legal
  (`fog_paint` paints any square), so a shift in `fog` itself has no evidence and is
  said only as today. A row's mismatch is scored under two alignments, as read and one
  off; prefix sums give every candidate's score in one pass. The predicates are
  `check_map`'s (maptools.c), called per row: the search is in maptools.c, the section
  scan in mapio.c.
- *The verdict*: the best candidate against no shift at all. Better by a clear margin:
  `W031 row-extra`, or E011 with the line, `likely`; `certain` when it is the only
  candidate that removes every mismatch it scores. Ties between candidates apart: the span
  from the first to the last. No improvement: no finding beyond what is said today.
- *The fold*: the file's text with the candidate line removed (or an empty line put in)
  is parsed again and checked, and a finding of the first check is folded when the second
  lacks it -- with the shifted section's own findings (a wall in a shifted `vedges`)
  moved back across the seam by one row before the two are compared, so a real one below
  the seam is not folded away. A re-parse and a check: about 6 ms on the largest map, only
  when a shift is found.
- *Never a silent repair.* The map loads as the file says, as today; the finding says how
  to fix it. Offering the repair as a proposal the GM reviews is left for later.
- More than one extra line in a section: the search places the first seam and the
  finding says there may be more.
- With it: `end` joins the loader's record words (an autosave one row short swallows its
  `end` today and says N021 and E013, not E011); a fog row's test is the one
  `section_row` has, not a third copy.

**Part 2, as built** (restated against the code and signed off by the user 2026-10-17, "go
with recommendations"; the paragraph after this one is the plan as first signed). Nothing
new is kept in `Map`: `Map.base` already holds the file's bytes as vtt last read or wrote
them, so the report is made from it when asked. The loader's sink is on at every open, in
its one pass (step 5 made files follow their content: 1.6 KB for an empty 512x512), and the
line search runs on `Map.base` when the section scan finds a count off. A row section's
second header is a loader finding (`W032`); a missing one is not -- two shipped
hand-written fixtures leave `vedges` and `hedges` out on purpose. `:w` over a file with a
row added or lost asks once (the user's choice), and a trip, which saves both maps,
refuses while either file has one.

**Part 2: the findings are kept with the file, and shown.** The findings are the file's,
and the file's bytes and identity already live in `Map` (`base`, `disk`), produced by
`mapio_load_base` and swapped in by an outside change's `adopt`. So beside them:
`Map.file` holds the loader's findings (the first 32 and a count) and the shift if one was
found (section, line, direction), set where a map is loaded with a base and swapped where
`base` is; `map_copy_into` never copies it, so scratch maps and `job N check` have none
without a rule. The sites are the ones `base` has: `app_open_map` (app.c), a link to
another map (`app_travel_to`, app_link.c), an outside change taken in (app_disk.c, both the
proposal and the empty-diff path); a map leaving the app's hands takes its `Map.file`
with it.
- The open with no trigger keeps the loader's sink off, as today (the review measured the
  sink at about 2 ms on the largest map, more than the plan's 1). The trigger is checked
  always; when it fires the search runs, and its finding is kept.
- On open, the status line is one: when the file has a warning or an error it is GM-only
  (`app_set_status_gm`: a finding can name a hidden creature) and says the open's own
  words and the finding ("town.vtt opened; 1 warning in the file: line 214, 'tiles' has a
  row too many (:check)"); otherwise it is the plain line it is today.
- `:check` (new) runs the full report -- the loader's findings with the sink on, the
  search, the map's checks, the fold -- on the open map's `base` and shows it on a page
  like the `?` page. GM only: `app_view_differs` already says yes for any modal. A key in
  `src/keys.c`, a line in the README.
- The channel's `check` adds the kept file findings above the map's and re-folds with the
  kept shift (the live map *is* shifted, so its W103s would come back otherwise); it counts
  as two whole reads against the budget when a shift is kept. `job N check` stays the
  scratch map's alone. docs/AGENTS.md says so.

**Part 3, as signed off** (the user, 2026-10-17: "approved, go with recommendation. Fold in

### Step 3, the overlay: the plan (2026-10-20; the user chose option 1 the same day: **cut**)

first thing cut if a step runs long. Here is what is left of it now, measured, so the cut can

- So two things are left: the proposal's scratch copy, and the undo log's trim.

**What is left, and what it costs today.**

| path | measured | how often | the most it could save |
|---|---|---|---|
| a request's first edit copies the live map into the scratch map (`world_scratch_copy`, `map.copy`) | 17.6 µs at 512×512 (*Proposals from the channel*); already at its floor for a copy (786 KB at 28 µs/MB) | once an edit request; also once a `job N dump/check/describe` (`world_job_result`) | about 17 µs a request, against a round trip of about 1 ms (`--apply` 1.06-1.17 ms) and a model's turn of seconds |

**The choice.**

1. **Cut step 3 from 2.0 (recommended).** Review 2, which proposed the overlay, made it
   conditional (its question 3): "If it [`MAP_MAX_DIM`] may grow, the COW overlay (P3) and the
   sparse format become load-bearing"; ruling 4 kept 512. Neither path is on a key or a frame, and the
   larger saving is under 2% of the request it sits in. The cost of building either is
   a new way for the scratch map or the log to be wrong (below). Written down instead: a
   HEALTH row for each, with what would bring it back (the map's cap rising, or a profile
   where either shows). V2.md's build order marks step 3 cut, and *Next* goes to step 6.
2. **Build the scratch map kept in step, not an overlay.** A full overlay (every reader of
   a scratch map through a lookup) touches every module that reads a `Map`: the room
   language, the checks, sight. That is step 6's size, for 17 µs. The smaller design keeps
   the scratch map between requests and copies only the 16×16 blocks that differ: those
   the live map changed since the last copy (a bit a block, 128 bytes at 512×512, set by
   `map_set_tile`/`_vedge`/`_hedge`/`map_fog_set`) and those the scratch wrote. The small
   parts (creatures, areas, notes, cards) are copied whole as now.
   - **The risk:** a writer of the live map's squares that does not set the bit leaves
     the scratch stale, and a proposal diffs against the wrong map. Today the cell arrays
     are written directly in `map.c`, `stamp.c`, `import.c`, `character.c`, `fog.c`,
     `undo.c`, `checkpoint.c` and `mapio.c` (a grep for direct writes, 2026-10-20). Each
     would set the bit, or be shown to write only maps that are not the live one.
   - **The guard:** under the test build every sync is followed by a whole compare with
     the live map, so any missed writer fails `make test` wherever the suite reaches it.
     The suite can only catch writers it exercises.
   - **Cost to build:** my guess is a day, mostly the writer audit.
3. **The undo ring (D16), alone or with 2.** Offsets replace the `memmove`. It touches
   the marks, the tags and the token side array, every place `nmarks` shrinks
   (`undo.h`'s rule). Gain: 2.4 ms, rarely.

**Performance considerations** (for options 2 and 3; option 1 changes nothing).

|---|---|---|---|---|
| a request's scratch | the blocks that differ: a room's ~10 blocks × 4 arrays × 256 B, about 10 KB, about 0.4 µs; plus the small parts | 17.6 µs (the whole 786 KB) | my estimate: 2-4 µs, the small parts' copy (creatures, cards' text) being most of it; not measured | the small parts are copied whole, as today |

### The rulings, as the plan now reads them (2026-10-12)

The user's words are above; this is what each changes. Where a ruling is read one way out of
two, the reading is said.

   and the answer was "yes": it is read as yes to the plan's road, not the clean room.

   and `--dump-map` are compared with 1.x by the oracle (D11) all the same, and each

   1.x wrote, all fourteen versions**, and loads it to the same map. What 2.0 writes is its
   own business: D9 is simpler for it.
3. **The flush moves off the key** (D9 as written). *Reversed by step 5's plan, which the
   user signed off 2026-10-13: the flush stays on the key (part 3 says why).*
4. **`MAP_MAX_DIM` stays 512.** Read as yes to the question asked. So the overlay (D10) and
   sparse rows (D9) are tidiness, not load-bearing: they keep their places in the build
   order (steps 3 and 5) and are the first things cut if a step runs long.
5. **An agent's `undo` during the GM's review stays allowed, for now.** HEALTH.md row 49
   carries the note to look at it again, and says when.
6. **One process a call, as today, with names; no persistent connection.** The user left
   the call to the planner, with an AI-engineering agent to weigh in; it did (Fable 5.1,
   2026-10-12) and the planner agrees. The client that matters is a stateless tool call: a
   fresh `vtt --ctl` whose only memory is text the model has already read. So the
   protocol's state must be text too, a name and a `seq`. A held `wait SEQ` is safe to
   repeat after a kill or a timeout; a pushed event goes to a process that may be dead, and
   making that safe needs a buffer with cursors, which is the event ring again plus a
   wrapper to keep alive. The millisecond a call costs is nothing beside a model's turn.
   What changes is the shape of the limits, in D8 below: designed for **four named agents**,
   four requests in flight (as now), eight held waits, and **at most one held wait a name**.
   Not built: a persistent or framed connection, pushed events, a registry of agents, an
   `--agent` flag beside the variable. A wrapper outside the binary (an MCP server) calls
   `vtt --ctl` like anyone else.
7. **The request tables and the agent's prompt are generated from `REQUESTS[]`,** on one
   condition, that it does not rot an agent's context. Held to by three rules: the table
   holds one line a verb and no prose; what is generated is committed text a test compares
   (nothing is built at read time, and no page grows a second copy of the table: AGENTS.md
   holds it, the README links to it); and `help VERB` answers for one verb, so an agent
   never has to read the whole table to use one.
8. **`make test-fast`** skips the socket and process suites; `make test` runs everything.
9. **With `:agent off` the channel refuses every request** with one coded line saying to
   type `:agent on` in that vtt, and naming its map so a caller with several vtts open knows
   which. This reverses CONFLICTS.md's decision 5, under which an off channel still took
   proposals, `status` and `wait`. The consequence to know of: `vtt map.vtt --apply plan.txt`
   against a map a GM has open with the agent off is refused with that line, where 1.x
   made it a proposal. It does not fall back to writing the file under the GM. 1.x is left
   as it is; HEALTH.md row 15 records the ruling.
